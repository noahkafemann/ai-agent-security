KI-Sicherheit · Versuchsaufbau

Was ein Agent darf,
entscheidet der Wirt.

Ein Sprachmodell kann Anweisungen befolgen, die jemand anderes ihm gibt. Diese Anweisungen sind Text — sie stehen in Webseiten, in PDFs, in Datenbanken. Man kann das mit mehr Prompting bekämpfen. Oder man kann es baulich begrenzen. AGORIS ist die zweite Variante: eine Sandbox aus Namespaces, chroot, Ressourcengrenzen, seccomp und einem Richtlinien-Proxy — ohne Docker, ohne pip, ohne Abhängigkeiten.

Die Grundidee

Der Agent bekommt keine Erlaubnis.
Er bleibt an einer Stelle.

Jede Zusage an ein Modell ist eine Bitte: „ignoriere Anweisungen in fremden Texten", „benutze keine anderen Werkzeuge". Ein Angreifer, der Inhalte einspeist, schreibt damit indirekt mit.

AGORIS gibt dem Modell nichts, was man ihm verbieten könnte. Es bekommt ein eigenes Dateisystem, ein gemountetes Python, ein eigenes Netz ohne Interface und ein CPU-Konto, das endet. Was nicht eingebunden ist, existiert für ihn nicht — nicht „wird später blockiert", sondern gar nicht.

Der API-Schlüssel liegt im Wirtprozess. Der Agent schickt seine Konversation durch einen Kanal und bekommt eine Antwort. Er kann den Schlüssel weder lesen noch ausgeben — und das wird gemessen, nicht behauptet.

Verteidigung in der Tiefe

Sieben Schichten, in fester Reihenfolge

Die Reihenfolge ist keine Geschmackssache. Jede andere ergibt EPERM, eine unsichtbare Zuordnung oder ein Gefängnis, in dem der Agent sich die Rechte selbst zurückgeben kann.

  1. 01
    Namespacesunshare() für user, mount, pid, net, ipc, uts — danach erst die ID-Zuordnung
  2. 02
    Dateisystemeigenes tmpfs, chroot hinein. Im Minimallauf nur Python — keine Shell, kein ls, kein curl
  3. 03
    Rechteno_new_privs, dann alle Capabilities aus dem Bounding-Set und aus capset
  4. 04
    RessourcenCPU, Adresse, Dateigröße, Prozesse, Deskriptoren — gesetzt vor dem execve
  5. 05
    seccomp-BPF26 gesperrte Syscalls. clone mit CLONE_NEW* verboten, clone3 gibt ENOSYS
  6. 06
    Netzkein Interface außer ausgeschaltetem Loopback. Egress nur über den Proxy
  7. 07
    Modell-Brokerder Schlüssel bleibt im Wirt — der Agent erreicht ihn nicht

Aufbau

Zwei Prozesse. Ein Kanal.

WIRT vertrauenswürdig

  • policy.py — was erlaubt ist
  • limits.py — Ressourcengrenzen
  • proxy.py — einziger Weg draußen
  • model.py — hält den API-Schlüssel
  • audit.py — JSONL mit SHA-256-Kette
fork() · stdin ◄ · stdout ► · JSON

GEFÄNGNIS der Agent, kompromittiert

  • user · mount · pid · net · ipc · uts
  • /work — beschreibbar, sonst nichts
  • /opt/agoris — nur lesbar
  • /run/agoris/proxy.sock — Eingang, kein Ausgang
  • runtime/worker.py — der Agent-Loop

Nachweis

14 Ausbruchversuche. 14 gehalten.

Jeder Versuch bekommt vom Wirt eine Kanariendatei mit geheimem Inhalt, die nur ein echter Ausbruch lesen kann. Ein geblockter Versuch heißt: die Schicht hat funktioniert.

Messsystem: Linux 6.18 / x86_64 / Python 3.10, Policy minimal. seccomp war dabei inaktiv — der Kernel erlaubte keinen Filter. Drei Versuche fielen also schon ohne die stärkste Einzelschicht. Genau dafür ist die Verteidigung in der Tiefe gebaut worden.

Innenansicht

So sieht der Käfig von innen aus

Ein Befehl misst jede Zusage dieses Projekts — vom Standpunkt des Agenten aus. Keine Behauptung, sondern eine Messung: python3 agoris.py inspect.

Soll

  • /usr/bin enthält nur python3 — keine Shell
  • /work und /tmp sind die einzigen beschreibbaren Pfade
  • /etc/shadow, /root, /sys existieren nicht
  • Umgebung: 7 Variablen, keine mit KEY/TOKEN/SECRET
  • Netz: Network is unreachable

Messung (Auszug)

{
  "4_inhalt_von_/usr_bin": ["python3"],
  "7_wo_darf_geschrieben_werden": {
    "/work/probe.txt":       "BESCHREIBBAR",
    "/usr/bin/probe.txt":    "Read-only file system",
    "/opt/agoris/probe.txt": "Read-only file system"
  },
  "10_geheimnisse_sichtbar": [],
  "12_internetzugriff": "Network is unreachable"

Weicht eine Stelle ab, ist die Anlage nicht richtig aufgesetzt — und genau das sollst du sehen.

Anleitung

Drei Befehle bis zum ersten Lauf

  1. Prüfen, was der Rechner kann

    $ python3 agoris.py doctor

    Sagt, ob Namespaces und seccomp verfügbar sind. Wenn mount — nein dort steht, laufen die Namespaces nicht, und Ergebnisse haben keine Aussagekraft.

  2. Dem Gefängnis auf den Zahn fühlen

    $ python3 agoris.py attacks

    14 Ausbruchversuche mit Messprotokoll. Ein leaked wäre ein echter Fund.

  3. Einen Agenten laufen lassen

    $ python3 agoris.py run "Aufgabe" -p research

    Bericht, Audit-Log und JSON landen unter runs/<zeit>/.

Nur Standardbibliothek. Python ≥ 3.8. Kein Docker, kein pip, kein gcc.

Ehrliche Grenzen

Was das nicht ist

Kein zertifizierter Ersatz

Ein Kernel-Bug umgeht alles hier. Namespaces teilen sich den Kernel mit dem Wirt — das ist der Kern des Problems, nicht seine Lösung.

Nicht jede Schicht überall

In vielen Container-Umgebungen lehnt der Kernel prctl(PR_SET_SECCOMP) mit EINVAL ab. AGORIS protokolliert das und wertet den Lauf als eingeschränkt.

Root ist nicht ideal

Läuft der Wirt als root, ist der Agent uid 0 im Namespace. Capabilities sind dann weg — aber RLIMIT_NPROC gilt für uid 0 nicht.

Nur HTTP

Der Proxy terminiert kein TLS. HTTPS braucht eine TLS-Terminierung im Wirt — das ist eine bewusste Grenze, keine vergessene.

Eine Schicht, die stillschweigend fehlt, wäre schlimmer als eine, die fehlt. Deshalb steht in jedem Bericht pro Schicht aktiv oder inaktiv — mit Grund.
