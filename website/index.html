KI-Sicherheit · Versuchsaufbau · Docker-ready

Was ein Agent darf,
entscheidet der Wirt.

Ein Sprachmodell kann Anweisungen befolgen, die jemand anderes ihm gibt. Diese Anweisungen sind Text — sie stehen in Webseiten, in PDFs, in Datenbanken. Man kann das mit mehr Prompting bekämpfen. Oder man kann es baulich begrenzen. AGORIS ist die zweite Variante: eine Sandbox aus Namespaces, chroot, Ressourcengrenzen, seccomp und einem Richtlinien-Proxy — ohne Docker, ohne pip, ohne Abhängigkeiten.

Was ist ein "Agent" hier? Jede Kombination aus Policy (was er darf) und Modell-Provider (wie er antwortet). AGORIS lässt sich damit testen, ob die Isolation bei jedem Agenten hält — nicht nur bei einem.

Die vier Sichtweisen, in die der Agent eingesperrt wird: eigene Benutzerrechte, eigenes Dateisystem, eigene Prozesse, eigenes Netz. moeglich heißt: dein Rechner kann das. Steht dort nein, taugt jede Messung auf diesem Rechner nichts.
Filterprogramm 504 Bytes, 26 gesperrte Syscalls
Die Liste der verbotenen Systemaufrufe. ptrace (sich an fremde Prozesse andocken), mount (eigene Dateisysteme bauen), pivot_root (aus dem Käfig ausbrechen), bpf (Kernel-Programme schreiben). Diese Zeile sagt nur, dass die Liste gebaut wurde — ob der Kernel sie annimmt, steht weiter unten im Bericht.
gehalten 14/14
14 Versuche, aus dem Käfig auszubrechen. Alle 14 sind gescheitert. durchgekommen 0 ist das eigentliche Ergebnis — eine Zahl ungleich 0 wäre ein Loch in der Anlage.

Die Grundidee

Der Agent bekommt keine Erlaubnis.
Er bleibt an einer Stelle.

Jede Zusage an ein Modell ist eine Bitte: „ignoriere Anweisungen in fremden Texten", „benutze keine anderen Werkzeuge". Ein Angreifer, der Inhalte einspeist, schreibt damit indirekt mit.

AGORIS gibt dem Modell nichts, was man ihm verbieten könnte. Es bekommt ein eigenes Dateisystem, ein gemountetes Python, ein eigenes Netz ohne Interface und ein CPU-Konto, das endet. Was nicht eingebunden ist, existiert für ihn nicht — nicht „wird später blockiert", sondern gar nicht.

Der API-Schlüssel liegt im Wirtprozess. Der Agent schickt seine Konversation durch einen Kanal und bekommt eine Antwort. Er kann den Schlüssel weder lesen noch ausgeben — und das wird gemessen, nicht behauptet.

Verteidigung in der Tiefe

Sieben Schichten, in fester Reihenfolge

Die Reihenfolge ist keine Geschmackssache. Jede andere ergibt EPERM, eine unsichtbare Zuordnung oder ein Gefängnis, in dem der Agent sich die Rechte selbst zurückgeben kann.

  1. 01
    Namespacesunshare() für user, mount, pid, net, ipc, uts — danach erst die ID-Zuordnung
  2. 02
    Dateisystemeigenes tmpfs, chroot hinein. Im Minimallauf nur Python — keine Shell, kein ls, kein curl
  3. 03
    Rechteno_new_privs, dann alle Capabilities aus dem Bounding-Set und aus capset
  4. 04
    RessourcenCPU, Adresse, Dateigröße, Prozesse, Deskriptoren — gesetzt vor dem execve
  5. 05
    seccomp-BPF26 gesperrte Syscalls. clone mit CLONE_NEW* verboten, clone3 gibt ENOSYS
  6. 06
    Netzkein Interface außer ausgeschaltetem Loopback. Egress nur über den Proxy
  7. 07
    Modell-Brokerder Schlüssel bleibt im Wirt — der Agent erreicht ihn nicht

Aufbau

Zwei Prozesse. Ein Kanal.

WIRT vertrauenswürdig

  • policy.py — was erlaubt ist
  • limits.py — Ressourcengrenzen
  • proxy.py — einziger Weg draußen
  • model.py — hält den API-Schlüssel
  • audit.py — JSONL mit SHA-256-Kette
fork() · stdin ◄ · stdout ► · JSON

GEFÄNGNIS der Agent, kompromittiert

  • user · mount · pid · net · ipc · uts
  • /work — beschreibbar, sonst nichts
  • /opt/agoris — nur lesbar
  • /run/agoris/proxy.sock — Eingang, kein Ausgang
  • runtime/worker.py — der Agent-Loop

Nachweis

14 Ausbruchversuche. 14 gehalten.

Jeder Versuch bekommt vom Wirt eine Kanariendatei mit geheimem Inhalt, die nur ein echter Ausbruch lesen kann. Ein geblockter Versuch heißt: die Schicht hat funktioniert.

Messsystem: Linux 6.18 / x86_64 / Python 3.10, Policy minimal. seccomp war dabei inaktiv — der Kernel erlaubte keinen Filter. Drei Versuche fielen also schon ohne die stärkste Einzelschicht. Genau dafür ist die Verteidigung in der Tiefe gebaut worden.

Agenten testen

Verschiedene Agenten. Eine Sandbox.

Ein "Agent" in AGORIS ist die Kombination aus einer Policy (was der Agent darf: Rechenzeit, Speicher, Dateien, Netz) und einem Modell-Provider (wie er antwortet: simuliert, echo, oder ein echtes Modell wie Anthropic Claude).

simulated

Deterministisch, ohne Netz. Ruft in fester Folge list_dir, write_file, finish. Für reproduzierbare Läufe und Vergleiche.

echo

Minimal-Anbieter: gibt die letzte Nachricht zurück. Für Verbindungstests — zeigt, dass der Kanal Wirt↔Agent funktioniert.

anthropic

Echtes Sprachmodell über die Anthropic-API. Der API-Schlüssel liegt im Wirt, nie im Gefängnis. Testbar mit AGORIS_API_KEY=… AGORIS_MODEL=…

Der Befehl python3 agoris.py test durchläuft alle diese Provider mit jeder Policy — doctor, inspect, run, attacks — und meldet klar, welche Schichten aktiv waren. So wird sichtbar, ob die Isolation bei jedem Agenten hält, nicht nur bei einem.

Innenansicht

So sieht der Käfig von innen aus

Ein Befehl misst jede Zusage dieses Projekts — vom Standpunkt des Agenten aus. Keine Behauptung, sondern eine Messung: python3 agoris.py inspect.

Soll

  • /usr/bin enthält nur python3 — keine Shell
  • /work und /tmp sind die einzigen beschreibbaren Pfade
  • /etc/shadow, /root, /sys existieren nicht
  • Umgebung: 7 Variablen, keine mit KEY/TOKEN/SECRET
  • Netz: Network is unreachable

Was der Befehl misst

  • Was steckt in /usr/bin?Liste der Programme, die der Agent starten kann. Nur python3 heißt: keine Shell, kein ls, kein curl.
  • Wo darf er schreiben?Der Befehl versucht, in fünf Ordnern eine Datei anzulegen und meldet das Ergebnis. Nur /work und /tmp dürfen.
  • Was ist nicht vorhanden?Prüft, ob Passwortdateien und Wirtspfade des Wirts im Käfig liegen. Sie dürfen nicht.
  • Sieht er Geheimnisse?Sucht die Umgebung nach Variablen mit KEY, TOKEN, SECRET. Die Liste muss leer sein.
  • Kommt er ins Netz?Versucht eine echte Verbindung. Network is unreachable ist das gewünschte Ergebnis.
Rohausgabe ansehen 
{
  "4_inhalt_von_/usr_bin": ["python3"],
  "7_wo_darf_geschrieben_werden": {
    "/work/probe.txt":       "BESCHREIBBAR",
    "/usr/bin/probe.txt":    "Read-only file system",
    "/opt/agoris/probe.txt": "Read-only file system"
  },
  "10_geheimnisse_sichtbar": [],
  "12_internetzugriff": "Network is unreachable"
}

Weicht eine Stelle ab, ist die Anlage nicht richtig aufgesetzt — und genau das sollst du sehen.

Anleitung

Vier Schritte bis zum ersten Lauf

  1. Prüfen, was der Rechner kann

    $ python3 agoris.py doctor

    Sagt, ob Namespaces und seccomp verfügbar sind. Wenn mount — nein dort steht, laufen die Namespaces nicht, und Ergebnisse haben keine Aussagekraft.

  2. Dem Gefängnis auf den Zahn fühlen

    $ python3 agoris.py attacks

    14 Ausbruchversuche mit Messprotokoll. Ein leaked wäre ein echter Fund.

  3. Einen Agenten laufen lassen

    $ python3 agoris.py run "Aufgabe" -p research

    Bericht, Audit-Log und JSON landen unter runs/<zeit>/.

  4. Alle Agenten testen

    $ python3 agoris.py test

    Prüft doctor, inspect, Agentenlauf mit simulated und echo-Provider, und die volle Angriffsbatterie — in einem Durchlauf.

Nur Standardbibliothek. Python ≥ 3.8. Kein Docker, kein pip, kein gcc.

Installation: git clone https://github.com/noahkafemann/ai-agent-security.git — mehr braucht nichts.

Windows — einfache Installation

AGORIS unter Windows mit Docker Desktop

AGORIS nutzt Linux-Kernel-Funktionen. Unter Windows läuft es deshalb am besten in Docker Desktop. Die Skripte unten behandeln auch die Windows-Meldung, dass der Herausgeber von Befehlsskripten nicht verifiziert werden kann.

1. Docker Desktop installieren

  1. Lade Docker Desktop für Windows herunter: docker.com/products/docker-desktop
  2. Installiere und starte den Rechner neu (falls gefragt).
  3. Aktiviere WSL2 als Backend: Docker Desktop → Settings → Resources → WSL Integration.
  4. Warte, bis das Wal-Symbol grün leuchtet.

2. Skript entsperren (wenn Windows blockiert)

Wenn Windows meldet: „Der Herausgeber kann nicht verifiziert werden“:

$ Set-ExecutionPolicy -ExecutionPolicy RemoteSigned -Scope CurrentUser

Oder starte mit Umgehung:

$ powershell -ExecutionPolicy Bypass -File install.ps1

3. AGORIS starten

PS> .\install.ps1 doctor
PS> .\install.ps1 test
PS> .\install.ps1 run "Hallo Welt" -p minimal

Oder in cmd.exe: install.bat doctor

4. Oder mit Docker Compose

$ docker-compose up
$ docker-compose run --rm agoris doctor

docker-compose.yml ist bereits im Repository enthalten.

5. Ohne Installation (Browser)

GitHub Codespaces — keine lokale Installation nötig:

$ Öffne das Repository in github.dev
$ Code → Open with Codespaces

Plattformen

Windows? macOS? — AGORIS läuft trotzdem.

AGORIS nutzt Linux-Kernel-Funktionen (Namespaces, chroot, seccomp). Auf Windows und macOS gibt es diese nicht direkt — deshalb stellt das Projekt mehrere Wege bereit, auf jeden Betriebssystem.

Linux

Direkt. git clone, python3 agoris.py doctor.

Windows

WSL2 (wsl --install) oder Docker Desktop. Alternativ GitHub Codespaces im Browser.

macOS

Docker Desktop oder GitHub Codespaces. Beide stellen eine Linux-VM mit allen Kernel-Funktionen bereit.

Eine Schritt-für-Schritt-Anleitung für alle Plattformen findest du in docs/INSTALLATION.

Ehrliche Grenzen

    
Was das nicht ist

    

      

        
Kein zertifizierter Ersatz

        
Ein Kernel-Bug umgeht alles hier. Namespaces teilen sich den Kernel mit dem Wirt — das ist der Kern des Problems, nicht seine Lösung.

      

      

        
Nicht jede Schicht überall

        
In vielen Container-Umgebungen lehnt der Kernel prctl(PR_SET_SECCOMP) mit EINVAL ab. AGORIS protokolliert das und wertet den Lauf als eingeschränkt.

      

      

        
Root ist nicht ideal

        
Läuft der Wirt als root, ist der Agent uid 0 im Namespace. Capabilities sind dann weg — aber RLIMIT_NPROC gilt für uid 0 nicht.

      

      

        
Nur HTTP

        
Der Proxy terminiert kein TLS. HTTPS braucht eine TLS-Terminierung im Wirt — das ist eine bewusste Grenze, keine vergessene.

      

    

    

      Eine Schicht, die stillschweigend fehlt, wäre schlimmer als eine, die fehlt.
      Deshalb steht in jedem Bericht pro Schicht aktiv oder
      inaktiv — mit Grund.
